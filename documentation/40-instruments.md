# Pinned instruments

The registry of harness-owned instrument content the spec has pinned. A crowded run is scoreable only against a procedure listed here with status **pinned**, and only when the per-run meta's recorded hash matches the pin (`10-harness.md` → "Crowding is part of the instrument"). A mismatch is an instrument defect: fix or re-pin (with rationale committed here) before any disposition.

## `answer-coverage@1` — pin record (2026-09-19, spec session)

**Hash measured** by recomputing SHA-256 over the UTF-8 bytes of the four numbered method lines in `30-checks.md`, joined by `\n` with no trailing newline, from the spec file itself: `211931382f74e072f2c2af8c77e678660f45efa4cd2082b8d9e25b2fd4be2d6a`. It matches the implementation's WO-4 report and the `method_hash` in the reported `measurements` entry. Identity pin with the usual caveat: it detects drift in the embedded text, and the implementation reports a test that asserts the embedded text is a verbatim substring of `30-checks.md`, so drift in either direction fails there too. A prose note beneath the numbered list is outside the hashed text by construction.

**WO-4 accepted (2026-09-19, from the report; commits c1168d3 and 989e722; 291 tests, 5 xfailed, ruff clean, live spend $0).** Verified against the spec: the hash (above); a real `measurements` entry from a fake-upstream row with every field of the WO-4 recording shape; the vector test named and parametrized over the seven table rows; the addendum's per-prompt `answers` keying. One discrepancy, reported as such by the implementation and settled here.

**The discrepancy, and the ruling.** The implementation reproduced every table cell except `furthest_offset` on the five cells whose furthest span ends on a collapsed whitespace run: it reported 6,766 where the table said 6,767 (pinned-r09 at both floors, floor-crowded) and 1,047 where the table said 1,048 (unpinned-r01 at both floors). The spec session recomputed the five rows on 2026-09-19 with a second, independently written reference implementation (rolling-hash longest-common-substring with the method's tie-break, recursion as stated, offset map carrying each collapsed run's raw first and last index). It found the same spans the implementation reported — on pinned-r09, (answer 426, reference 0, length 5,773) and (6,200, 5,774, 224); on unpinned-r01 at floor 64, three spans ending at normalized 959 — and the same raw cut points: `Defense.` then `\n\n` at raw 6,764–6,765 then `[[Page 137`; `CONTENTS.` then six whitespace characters at raw 1,041–1,046 then `(a) Divisio`. Under the method text, the span's last normalized character is the space that replaced the run, and one past the run is 6,766 and 1,047. No reading of the numbered text yields 6,767: that is one past the run plus one, the value an instrument produces if its offset map sends a collapsed space to the raw index *after* its run and then adds one. The 2026-09-18 vectors were computed with such an instrument, so the table was wrong on exactly the cells where a span ends on collapsed whitespace, and right on every cell where it does not (pinned-r01's 19,958 and the claude-code floor-40 span, both ending on a non-whitespace character, reproduce under both instruments). A finding is only as valid as the instrument that produced it; the instrument was the spec session's own. **Ruling:** the five cells are corrected to the method's values (table above, corrected 2026-09-19); the reading is pinned as a note beneath the method in `30-checks.md` without touching the hashed lines — a normalized space that replaced a whitespace run came from the whole run, and `furthest_offset` for a span ending on it is one past the run's last raw character. The implementation's strict-xfail test holding the old values is retired by WO-5.

## `loop-scaffold@1` — pin record (2026-09-18, spec session)

**Hash measured** by executing `LOOP_SCAFFOLD_V1.content_hash()`; the value matches the implementation's report (WO-1 §1) and the `scaffold.content_hash` recorded in every loop cell's `meta.json`, every `cell_gates` tuple, and every probe-cache entry across the 2026-09-18 runs (`runs/2026-09-18-q8-*`, `runs/2026-09-18-loop-smoke`). Identity pin, same caveat as the crowding pins: obtained by running the instrument, so it detects drift rather than certifying what the code hashes over; the report states the hash covers name, version, system prompt, step cap, tool-loop policy text, probe tool definition, and probe prompt.

**Content review against requirement 1 and no-disclosure (`50-drivers.md` → loop; `10-harness.md`).** System prompt, verbatim from the report: "You are a helpful assistant with access to tools. When a tool can supply information you need, call it instead of relying on memory. Base your answer on what the tools return, cite or quote retrieved material where that matters, and say plainly when something could not be determined with the tools available." Verdict: generic, domain-neutral, no mention of testing, harnesses, or evaluation; it does instruct tool-first behavior and honest non-determination, which is a scaffold choice the suite's Layer-2 criteria must be read against (a consumer told to say plainly what could not be determined is being nudged toward the floor behaviors the criteria score — the loop measures server × model *under this nudge*, and that is what S11 means by "under a pinned harness scaffold"). Step cap 24 requests per turn, fresh per pre-turn and scored turn. Tool-loop policy: one request per step, tool results appended as text joined by newlines (JSON serialization when no text), no `tool_choice` sent, turn ends on a call-free response or at the cap. Probe tool `get_probe_value(key)`, probe prompt asks for key `alpha`. Not in the hash but sent on every request: `usage.include` and the strict-routing provider block; tools offered under the `mcp__<server>__<tool>` idiom so wire surfaces compare across drivers. Recorded as adequate for v1. Two things a v2 would want, noted so they are not forgotten: the join-with-newlines flattening discards MCP result structure (image or resource items never reach the model), and the cap applies per turn rather than per conversation. Third, observed 2026-09-18 across the C1 provider-pin runs: the prompt carries no audience guidance (nothing says the person cannot see tool parameters or results) and "cite or quote retrieved material" nudges toward pasting a window verbatim; `openai/gpt-oss-120b` at low effort relayed the server's continuation instruction (`start_char=20000`) to the user word for word under this scaffold, while `openai/gpt-5.4-nano` under the same scaffold rephrased it in user terms — so the effect is model-dominated, the scaffold contributes, and any v2 that adds audience guidance is a new pinned version whose cells never pool with v1 (S11). The behavior itself is a consumer-behavior finding handed to the suite's spec session, not an instrument defect. **Fourth, 2026-09-21 (S16 corollary; maintainer):** v1 ends the turn on any call-free response, including one whose content is null because the model wrote its tool call into the reasoning channel (7 of 26 rows in one uscode-mcp run; `10-harness.md` → Layer 2). A re-prompt or retry on such a response is a change to the tool-loop policy, which is inside this hash, and it would change what the floor measures — a consumer that fumbles a call and is rescued is a different consumer from one that is not. So a retry exists only as `loop-scaffold@2`, pinned and reviewed like v1, with its own cells; v1 stays as it is and keeps measuring the unrescued floor. Not ordered: whether a v2 is wanted at all is the maintainer's question, and the first evidence for it would be the rate of `null_final_content` rows once WO-7 makes them countable.

## `neutral-file-triage@2` — pin record (2026-08-31, spec session)

**Hash measured** by executing `NEUTRAL_FILE_TRIAGE_V2.content_hash()`; the value matches both the implementation's report and the `crowding.content_hash` recorded in the live run's meta (`runs/2026-08-31-driver-proof/smoke-crowded/S/S1/meta.json`) — the pin, the code, and a real run agree. Same identity-pin caveat as v1: obtained by running the instrument, so it detects drift rather than certifying what the code hashes over.

**Content review against S6:** identical notes, folders, and distractor server to v1; the only delta is the opening prompt, which now bounds the pre-turn to the first four notes and leaves the rest explicitly pending ("we'll keep going in a bit, and the rest MUST wait until you get the go-ahead"). Verdict: satisfies "genuinely mid-way through" — the scored prompt lands inside an owned, unfinished task. Judgment note: an explicit hold is the implementable form of interruption in a turn-based driver (a pre-turn cannot be cut off mid-generation), and pending-and-owned work is the competing goal S6 wants present; recorded as adequate, not merely tolerated.

**Mid-task property verified from artifacts, not the report:** the live run's `distractor-state.json` shows exactly `n01`–`n04` filed at scored-turn time — 8 of 12 notes remained, and the scored turn's answer came via a traced SUT call while the crowding state persisted beside it.

**Mid-task predicate, pinned (ruling S19, 2026-09-21; implemented outside the content hash, WO-10 accepted 2026-09-22 — the pin for the predicate is this text, and a change to it is a spec commit here):** at scored-turn time the filed set in `distractor-state.json` is exactly `{n01, n02, n03, n04}`; folders are unconstrained (the model's filing choices are its own, not the precondition). Fewer filed is a pre-turn that did not get through the task; more is v1's post-task defect. The harness checks this after the pre-turn on every driver and marks a failing row precondition unmet, cause `state_mismatch`; until the harness does (WO-10), a scorer applies it by hand. **Scan of the record, 2026-09-21 (spec session):** 87 live rows under this procedure across both repositories, fake-upstream acceptance runs excluded — 76 reached the scored turn at exactly `n01`–`n04`; 8 were unmet or failed at 1–3 filed; **3 reached the scored turn at the wrong state**, all in `uscode-mcp/runs/2026-09-21T01:13:27-04:00-loop-complete/loop-floor` (A3 at `{n01}`, A2 and C2 at `{n01, n02}`), all three pre-turns having ended on S16's null final before WO-7 made that an exit-4 outcome. **Handed to the uscode-mcp spec session:** those three rows are not mid-task under S6 and are instrument-defective for the crowded condition; any crowded-condition finding scored from them should be re-examined, and the rows' fresh-cell siblings are unaffected. The disposition is theirs.

## `neutral-file-triage@1` — superseded (S6 defect, found 2026-08-31)

The v1 pre-turn ran the triage to completion ("Inbox is now empty" before the scored prompt), so the scored turn landed **after** the competing goal was gone — the cell measured a post-task consumer, not a mid-task one, violating S6's "genuinely mid-way through". Disposition: **any crowded result produced against v1 is instrument-defective for the crowded condition and is not scored** (`10-harness.md`, instrument defects block all other dispositions). No such result was ever scored — the defect was caught in the driver-proof run before any suite used the cell. The v1 identity pin is retained above so drift in the still-registered v1 content remains detectable (the implementation keeps a test asserting the v1 hash).

This finding is also the first live datum on the Q5(b) question's territory: completing-vs-pending is evidently a real axis of crowding strength, which sharpens what the padding-vs-task experiment should control for if it ever runs.

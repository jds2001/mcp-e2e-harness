# Driver attribution contracts

What a driver must establish before it may host cells, per driver. The general obligations are in `10-harness.md` (two-source attribution, S7 wire-first verification, S8 fail-fast liveness, S9 operator legibility) and Q2 in `90-open-questions.md`; this file is the per-driver record of how each driver meets them. A driver absent from this file may run exploratory cells, but no attribution-dependent conclusion is scored from it.

Evidence discipline: a driver's entry cites either harness-instrument measurements (the standard that settles Q2 for that driver) or attributed external measurements (which specify the driver but do not settle Q2 — the settling run must happen under this harness's own instruments). Every entry is version-pinned; a driver version bump voids the verification until re-measured.

## codex — verified 2026-09-01; Q2 settled (one narrow residual below)

Source: `codex-driver-handoff.md` (measurements by the uscode-mcp spec session on codex-cli 0.147.0, kept there as its O31–O35, probe recipes included). These are attributed external measurements: they are the basis for the requirements below, and they do NOT settle Q2 for codex — that takes the implemented driver re-demonstrating the effects under this harness's own recording.

Binding requirements for the implemented driver:

1. **API-key credentials only; ChatGPT-login state is refused for attribution cells.** Measured: under ChatGPT login a custom provider still received `web_search` in the tools array, so the noweb mechanism is unproven there; and the credential-isolation measurement (Authorization to a custom provider carries exactly the `env_key` value) means a custom-provider backend cannot ride ChatGPT credentials anyway.
2. **Isolated `CODEX_HOME` per invocation, harness-authored.** Load-bearing for attribution, not hygiene: ambient user config leaked MCP servers and plugin tools into the offered surface, and one ambient server (`node_repl` — arbitrary Node, a network-capable channel) started and ran mid-probe. The codex analogue of the neutral working directory.
3. **Web disable via the noweb custom-provider mechanism, never the config knob.** `tools.web_search=false` was measured dead under both auth modes (web tool live and used, 7–9 invocations, including sandbox-evasion attempts via an r.jina.ai proxy fetch and DNS-over-HTTPS). Mechanism: web-tool registration follows the provider's `supports_standalone_web_search` declaration; builtins declare it immutably, custom providers declare nothing. `wire_api = "responses"` (0.147.0 refuses `"chat"`).
4. **The custom provider IS the harness recorder.** The noweb mechanism and S7's API-boundary capture are the same interposition point: the driver points codex's custom provider at the harness's recording proxy, which forwards to the real backend. One mechanism yields both the web-disable and per-scored-invocation wire verification. Same recording rules as the claude-code recorder: tool names only, never headers (the provider Authorization header carries the real API key), never message content.
5. **Per-invocation effect verification, S7 semantics.** A `web_search` (or any non-MCP network tool) in a wire-captured tools array, or a web-search event in the run record, is an instrument breach: the row is not tool-attributable, the cell is BROKEN. The rationale is the handoff's sharpest exhibit: a present-but-inadequate web tool did not merely leak — it manufactured a fabricated fetch result presented as retrieved (n=1, but the failure class is exactly what attribution cells exist to exclude), so refusal must be hard, not best-effort.
6. **Key injection for spawned MCP servers.** Codex sanitizes the environment of MCP servers it spawns (canary measurement: `PATH`/`HOME` present, parent-env canary absent), so the manifest's `{"$secret": …}` resolution must reach the server by a spawn-helper that injects into process env only — never into the generated codex config (a file artifact) nor `meta.json`'s recorded command. The existing secret-hygiene scan applies to the generated codex config like any artifact.
7. **Native vocabulary, as everywhere**: codex cells carry `reasoning_effort` and friends verbatim; no mapping to Claude's `thinking` exists or is recorded.

**Verification record (2026-09-01, spec session, from artifacts).** All settling evidence produced under this harness's instruments and re-verified from the run directories: wire capture across a live cell (gpt-5.6-luna, 3/3 requests) showing the 16-tool code-mode surface — codex's own harness tools plus exactly the three MCP tools, no web tool — with `reasoning_effort` verbatim and codex-cli 0.147.0 pinned in meta; a traced MCP call grounding the answer; zero web events, zero unparseable requests, zero forward errors; and the requirement-6 canary: a SUT that refuses to start keyless served normally, the secret reached it via the mode-0600 secrets file whose *path* alone appears in the generated config, the value appears in no artifact, and the file was deleted at invocation end (`spawn-check.json` records delivery without the value). 174 tests pass under the spec session's own run.

**Ruling — code-mode surface semantics.** Codex code-mode models send no `tools` array; the roster travels as the client's declaration (`code_mode_tool_names` in request metadata), which the recorder captures with per-record `tool_source`. The declaration is wire-observed and nothing model-mediated, but it *describes* the served toolset rather than constituting it. Ruled sufficient for S7 **only as a conjunction**, never alone: declaration shows no web tool AND zero web events in the run record (the effect check that would catch a backend-injected tool actually contributing) AND the noweb provider mechanism in place (the causal preventer of backend web registration). For tools-array models the array remains the standard, and the harness's enforcement (web tool in array → cell BROKEN) is test-verified instrument behavior. Per-record `tool_source` keeps the two standards distinguishable in every artifact.

**Ruling — `external_web_access: false` earns no exception, ever.** This driver's record exists because a config knob was measured dead; a config assertion never substitutes for observation regardless of its name (S7). If a future codex version makes such a flag real, the path is re-measurement under harness instruments and a new entry line here — not an exception.

**Residual 1 — exec-channel egress: CLOSED 2026-09-01.** The harness-instrument canary ran live (`runs/2026-09-01-codex-egress-canary`, re-verified by the spec session): the event stream shows the actual command executing in the neutral cwd, the actual sandbox failure (`curl: (6) Could not resolve host`), the consumer answered the exact protocol string, and the wire capture during the canary shows the code-mode surface with no web tool; 0.147.0 pinned. The sandbox-blocks-egress claim is now a harness-instrument observation. Verdict semantics honor the discipline: only the exact protocol string passes — a reported fetch and a fabricated one are indistinguishable by design, so both fail into investigation; empty answers are BROKEN, never blocked. The canary re-runs on codex version change, like all driver verification. Standing rule regardless: a recorded exec event that touches the network in any cell is an instrument breach, same class as a web tool on the wire; exec event streams stay in the per-invocation artifacts for exactly this review. `claude-code` declares no egress-probe shape — its surface removal leaves no shell channel, and the canary refuses to apply rather than measuring nothing.

**Residual 2 — CLI-level network activity: CLOSED 2026-09-01, under continuous verification.** The disableability measurement was run, not asserted (implementation session, five fresh isolated homes, with a baseline showing the fetch happens at CLI startup independent of turn outcome — a 401 invocation still fetched): `features.plugins=false` suppresses the fetch; `features.remote_plugin=false` and `plugins.marketplaces=[]` are dead knobs. The working flag is in the driver argv and asserted in the attribution record — but, given this CLI's measured history of dead knobs, it is **trusted only under continuous observation**: `environment_state.plugin_sync` (the fetched SHA, or null) is recorded in meta on every scored invocation and in both probes, captured after the turn since vendor-pushed state lands mid-invocation. A non-null SHA on any invocation is environment drift, surfaced rather than silently absorbed. Spec-session re-verification from the live fix-verify run: `.tmp` absent from the home entirely, `fetched_sha: null`, the flag in argv, and the egress canary still passing clean. The closure standard here differs deliberately from Residual 1's: a one-time settling run was not required for the knob itself, because per-invocation observation of the effect is strictly stronger than any one-time proof. Original finding, for the record: The codex CLI performed its own network I/O during the canary invocation: the isolated `CODEX_HOME` contains a shallow clone of `https://github.com/openai/plugins` with `FETCH_HEAD` at `1e285826e604f66f7208f7ac4dba0fe8341d1f57`, fetched mid-run despite the ephemeral home, the noweb provider, and the read-only sandbox — those govern the *consumer*; plugin sync is the *CLI* acting on its own. This does not reopen the egress settlement (different actor, different channel), and the wire capture remains the backstop against plugin-*injected tools* reaching the model. What it does threaten is environment determinism and the two-source rule's environment half: vendor-pushed state enters the instrument at run time, so two invocations of the same cell need not run the same CLI behavior. Required of the driver now: record the plugin sync state (the fetched SHA, or its absence) in meta per invocation, so drift is detectable — the evidence is already in the home directory, it just needs lifting into meta. Open measurement, not to be asserted from config documentation: whether 0.147.0 offers a working way to disable plugin sync (this CLI's config knobs have a measured history of not doing what they say).

## loop — verified 2026-09-18 (Q8 settled for pinned cells; two residuals below)

Ruled into existence by S11 (`00-INDEX.md`): the second driver family. The harness supplies the consumer itself — a minimal MCP client and tool loop speaking to any OpenAI-compatible endpoint. OpenRouter is the first intended deployment (one driver, many vendors and capability tiers); a direct vendor endpoint is the same driver with a different base URL. What a loop cell measures is **server × model under a pinned harness scaffold** — deliberately not the behavior of any shipping product. Motivation: capability breadth (the `capability-floor` role currently reaches only models the two product CLIs expose) and attribution by construction (no builtins exist to remove; the tools array is exactly what the harness constructs).

Binding requirements for the implemented driver:

1. **The scaffold is instrument content — S6 treatment.** The loop's system prompt, tool-loop policy, and turn/step caps are harness-owned, versioned, and content-hashed in `40-instruments.md`; the scaffold version joins cell identity. Two cells differing only in scaffold version are different cells and never pool.
2. **Wire capture interposes; it never trusts the loop.** The harness being its own consumer earns no exemption from S7/S10: the recorder observes actual outbound traffic under the standard recording contract (`10-harness.md` — tool names, body keys, sizes; no headers, no content), never a reconstruction of what the loop intended to send.
3. **S7 per-invocation verification still runs.** The wire tools array must equal the manifest surface exactly on every scored request; any extra tool (endpoint- or router-injected) is an instrument breach, cell BROKEN.
4. **Served-provider identity, recorded per request.** On OpenRouter a model id is an insufficient pin: the same id routes across backend providers with different serving stacks and quantizations, so provider identity is the environment half of the two-source rule here. Every invocation records the provider the response metadata reports as actually serving each request. **Pinned cells:** the provider pin joins cell identity and `require_parameters` is set; a served-provider mismatch breaks the cell. **`require_parameters` is set on every loop request, pinned or not** (hardened 2026-09-18 from the P-knob-drop observation in `openrouter-probe-2026-09-18.md`: without it the router silently dropped an unsupported knob; with it the router refused loudly). For an unpinned cell the flag narrows routing to endpoints declaring every knob sent, which is the only acceptable meaning of "unpinned". **What the pin verifies, stated exactly (2026-09-18, from WO-1 finding 1):** a response identifies its server by provider display name only (`provider: "DeepInfra"`), so the served-provider check verifies the **provider slug** of the pin and nothing finer; the quantization component of a pin tag (`deepinfra/bf16`) is sent as `provider.quantizations` and enforced by the router on its own declaration, and no artifact can confirm it. A pin's identity in artifacts is therefore slug-verified, quantization-asserted, and reports must not say otherwise. Non-2xx responses carry no provider and are recorded as error responses, never judged against the pin; a **2xx** response without a provider is the mismatch. **Unpinned cells run; they are marked, never refused** (maintainer, 2026-09-11): the quick "how do small models handle my tools" pass is a legitimate use of a public harness, so unpinned cells execute normally and every report row they produce carries `reproducibility: unpinned` plus the observed served-provider set. The mark travels with the row into every downstream artifact; stripping it is a reporting defect.
5. **Knobs verbatim; honoring is unproven until Q8 P-knob-drop runs.** Knobs go to the endpoint in its native vocabulary and are recorded verbatim, as everywhere. Whether an unsupported knob is refused, flagged, or silently swallowed by the routing layer is the preregistered measurement. First datum (2026-09-18, external instrument, N=1): **silently swallowed without `require_parameters`, refused with it** — hence the hardening in requirement 4. What the flag cannot give is backend honoring of a declared knob, so the calibration-probe route stays: a scored conclusion that depends on a knob's effect (reasoning effort above the model's minimum, most likely) needs a per-knob, per-provider probe whose observable is the effect itself (reasoning-token counts in usage, for effort), recorded beside the cell.
6. **Cost legibility before the first invocation — S9 kin.** Operators bring their own keys, and a matrix multiplies fast (cells × invocations × models). The runner states up front: the invocation count and an estimated spend where the endpoint publishes per-model pricing, labeled an estimate; and it honors a budget cap (config or flag). Hitting the cap stops the run cleanly — completed cells stand, the stop is a surfaced run-level outcome, never silent. Actual usage and cost from response metadata are recorded per invocation where returned.
7. **Data-policy disclosure, deny-by-default.** Some providers behind OpenRouter log prompts and completions and may train on them, and suites will point this harness at servers whose returned data the operator has not pre-screened. Default: the driver sets OpenRouter's provider preference excluding such providers (`data_collection: "deny"`) and surfaces the applicable per-provider policy in the pre-run output. An operator may opt out explicitly; the opt-out is recorded in meta. **Honesty limit, stated now so it cannot be laundered later:** provider policy is OpenRouter's published assertion and backend behavior is unobservable from here — this requirement is a disclosure plus a routing preference, not a verified privacy property, and no artifact may present it as the latter. What *is* measurable is whether the preference steers routing at all (Q8 P-data-policy-routing). **Amended 2026-09-18 (WO-1 finding 2):** OpenRouter's public API carries no per-provider logging or training mark — neither the endpoint listing nor the providers listing has one; the per-provider policy exists only on the website. So the disclosure is what the API publishes (each pinned provider's policy and terms URLs, headquarters, datacenters) plus the preference sent, and the **only enforceable privacy instrument is the provider pin** to a provider whose policy the operator has read. Measured: under deny and under allow the served set over 20 draws each was the same two providers, so the preference did not observably narrow routing between them; that is recorded as a null result on steering, not as evidence about logging.
8. **Family separation — S11.** loop cells never pool with product-driver cells and never substitute for them, in either direction. Whether a loop cell gates is the suite's decision like any other cell; the harness's obligation ends at making the family, scaffold version, and reproducibility mark legible in every artifact.

9. **Eligibility is an endpoint property, verified by probe — S12.** "Supports tools" is asserted at two levels on OpenRouter and they disagree: the model-level `supported_parameters` flag says yes for a model id while individual endpoints behind that id say no (measured exhibit below). So a model id is never eligible; a (model, provider) pair is, and only after a **tool-capability calibration probe**: a discarded invocation under the cell's exact scaffold, knobs, and pin, against a harness-owned trivial tool, which must return one well-formed tool call — name in the offered surface, arguments parseable and schema-valid — within one turn. Probe results are cached per (model, provider tag, scaffold version, driver version, **knobs**) with the date — knobs joined the tuple on 2026-09-18 because the verdict measurably depends on them (`openai/gpt-5.4-nano` fails the probe with `temperature` and passes without); a cache entry is voided by any change in that tuple. Only pass and fail are cached; a probe that could not run (upstream 429 or 5xx after retries, timeout) is `broken`, uncached, and the cell is refused for that run without a verdict being recorded against the pair. A probe failure refuses the cell as instrument-broken before any model turn is spent (S8 kin). Unpinned cells probe against whichever endpoint served the probe and record which; the reproducibility mark already says the rest.
11. **Repeats are not samples until shown to be (2026-09-18).** A pinned endpoint can be near-deterministic at the endpoint's default sampling — the driver sends no `temperature` or `seed` unless the cell's knobs carry them, which is correct (knobs verbatim) and means repeat invocations may replay one draw. Measured on the P-provider-pin run: the pinned `deepinfra/bf16` arm produced **6 distinct answers in 10 invocations** (four byte-identical, one further pair identical) while the unpinned arm produced 10 distinct answers from two providers. So an invocation count is not a sample count, and any behavior-rate claim from a loop cell ("0 of 10 offered the link") states both the invocation count and the distinct-answer count. The driver records the distinct-answer count **per prompt within a cell** (answer digest, deduplicated) beside the invocation count in the run manifest (WO-3 delivered the digest per row and the count per cell; WO-4's addendum keys the count by prompt, because two prompts differing is not the determinism question). Across runs — the shape the Q8 repeats actually had, one invocation per run directory — the per-row `answer_sha256_16` is what a scorer aggregates. **Stated plainly 2026-09-21, a gap the spec session owns:** the runner has no repeat mechanism (`mcp-e2e run --help` on harness 1950fbb offers `--cells`, `--groups`, `--prompts` and nothing that repeats), so within one run a (cell, prompt) pair is invoked exactly once and the per-prompt count is structurally `invocations: 1, distinct: 1` — a count that cannot vary, which is the dead-defensive pattern the conventions warn about, ordered by this session in WO-4's addendum without checking that a run could reach it. Until Q9 (`90-open-questions.md`) is answered, N invocations means N runs with distinct `--run-dir`, and the distinct-answer count is the scorer's aggregation of `answer_sha256_16` over those rows. A suite that wants variance sets `temperature` or `seed` in knobs where the pinned endpoint declares them, and says so in the cell's notes; the comparison it then makes is against a cell with those knobs, never against a default-sampling cell.
10. **Reasoning tokens are spend.** On reasoning models the completion side of the bill includes reasoning tokens, which at medium or high effort can exceed the answer by an order of magnitude; the pre-run estimate (requirement 6) states this as the unbounded term, and floor cells carry the model's minimum effort unless the suite's question needs otherwise.

Manifest shape: frozen in `20-manifest.md` → "Loop-driver cells" (2026-09-18); the concrete consumer the 2026-09-11 deferral waited for was the maintainer's own floor use.

**Measured exhibit for requirement 9 (2026-09-18, spec session; reproduce with `GET https://openrouter.ai/api/v1/models/openai/gpt-oss-120b/endpoints`, no key needed).** The catalog lists `openai/gpt-oss-120b` with `tools` in its model-level `supported_parameters`. Its endpoint listing that day had 24 endpoints, of which **5 did not advertise `tools`** (DigitalOcean, Google Vertex, both Amazon Bedrock regions, SiliconFlow); quantization ran across bf16, fp8, fp4, fp16, and "unknown"; list price ran from $0.03 to $0.35 per million input tokens; and 7 endpoints carried a degraded status with 30-minute uptime between 85% and 94%. An unpinned request to that id can therefore be served by a backend that will not call tools at all (the cell BREAKS on the S7 check — loud, but wasted) or by an fp4 quantization of a model the suite thinks it pinned. The same shape recurs at smaller scale on `openai/gpt-oss-20b` (4 of 13 endpoints without tools), `google/gemma-4-31b-it` (the cheapest endpoint is the one without tools), `meta-llama/llama-4-maverick` (2 of 5 without), and `minimax/minimax-m3` (1 of 13). First-party-only models (`qwen/qwen3.7-flash`, `mistralai/mistral-small-2603`, the OpenAI, Google, Anthropic, and xAI vendor endpoints) have no such spread, which is a reason to prefer them when the pin question is not worth the operator's attention.

**Cost model, grounded in real request sizes (2026-09-18).** The wire recorder's Q7 sizes give the input side directly. From uscde-mcp C1 under claude-code: a crowded floor invocation summed 586,489 request bytes across 14 model requests; a fresh isolation invocation 128,544 across 4; a fresh ceiling invocation 49,150 across 3. The one measured tokens-per-byte ratio is 37,193 tokens for a 105,242-byte body (2.83 bytes/token, Anthropic tokenizer; other tokenizers differ, call it ±30%). So a crowded floor invocation is ~200k input tokens and a fresh one ~20–45k; at $0.15/M input that is ~$0.03 and ~$0.005 respectively, before output. Output is the answer plus tool-call arguments plus reasoning, typically under 5k tokens at minimum effort. Order-of-magnitude consequence, stated so budgets are set with eyes open: a 20-prompt suite across a crowded floor and a fresh isolation cell (40 invocations) costs on the order of **$1 at the $0.15/M open-weight tier and $0.25 at the cheapest pinned endpoints**, and about **$10 at the $1/M vendor tier** — the loop scaffold replaces the product CLI's system prompt, so the loop numbers will differ from these by a constant, not an order of magnitude. Requirement 6's cap is what protects against the terms this estimate cannot bound: reasoning tokens at high effort, and runaway tool loops, which the scaffold's step cap must bound.

**Loop-specific cost basis (2026-09-18, from the Q8 runs, harness recorder):** the claude-code basis above overestimates loop spend by an order of magnitude, because the loop scaffold carries no product system prompt. Measured on uscde-mcp C1 at `openai/gpt-oss-120b` @ `deepinfra/bf16`, reasoning low: a **crowded floor** invocation was 12 requests, 46,577 prompt tokens, $0.0021; a **fresh isolation** invocation 2 requests, ~9,900 prompt tokens, $0.0006–0.0011. So a 40-invocation pass is about **$0.06 at that pin and about $0.25 at the $0.15/M list tier**; the vendor tier scales by price the same way. The unbounded terms stand: one unpinned invocation paged three ~413KB windows and hit the endpoint's context limit at $0.004, and one took 356 s on a slow backend. The runner's estimate should use this basis for loop cells (WO-2).

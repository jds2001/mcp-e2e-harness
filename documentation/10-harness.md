# The verification contract

The harness drives a real consumer model against an MCP server under test, through a real driver (an agent harness such as Claude Code headless), and records what happened. Humans and the suite's spec session score the results against criteria pinned in advance. The harness is generic; everything server-specific arrives in a **suite** — a manifest plus its groundings and checks, owned by the server project's own repository (ruling S1, `00-INDEX.md`).

This file is the contract for the harness itself. The interface a suite must satisfy is `20-manifest.md`; the Layer-1 check language is `30-checks.md`. The ancestor of this design is congressMCP's §17 harness, preserved verbatim in `examples/congressmcp/` — historical claims below (the A3/B3/E3 invalidations, the zero-trace incident) refer to that record.

## Division of labor — binding

The harness **executes and records; it never scores.** Every prompt carries its `pass`/`fail` criteria pinned before the run — preregistration-of-scoring — and a criterion is never edited after seeing a result it would score. Criteria change only between runs, with the rationale committed in the suite repo. Scoring is done by a human and/or the suite's spec session, recorded beside (never instead of) the raw artifacts.

The manifest is normative and lives in the suite repo. The harness loads that file verbatim — no harness-side copy, no transcription, no defaults silently merged in. Manifest edits are suite-repo spec commits. **Applied 2026-09-18 to the loop driver's settling runs:** the Q8 runs used a harness-side derived copy of the uscde-mcp manifest with loop cells substituted, acceptable for settling the instrument (the runs measured the driver, not the suite) and not acceptable for any scored row — the copy went stale the moment the suite revised C1. Loop cells a suite wants scored are authored in the suite's own manifest by the suite, like any cell; the derived copy is retired, never re-synced.

Corollary for this repo: the harness implementation contains **no knowledge of any particular MCP server**. Any server-specific constant, tool name, cache path, fixture, or check found in the harness code is a defect against this contract. The implementation session should treat de-specializing the seeded code as conformance work against this file and `20-manifest.md`.

## Layer 1 — mechanical trace conformance (harness-evaluated)

Assertions a program can check against every trace record, with no judgment involved. The suite supplies them as declarative rules in the manifest (`checks`, ruling S2); the harness evaluates them and reports per-check results beside the run. What those rules assert is the suite's business — they encode the server's own tool contracts (the congressMCP suite asserted error-envelope structure, truncation markers, provenance completeness, and so on against its `40-tools.md`; see the example).

Exactly two Layer-1 behaviors are built into the harness rather than supplied by the suite, because they protect the instrument rather than the server contract:

- **Secret hygiene**: no configured secret material (anything the server registration marked as secret, plus values of env vars the suite names as sensitive) appears in any trace record, transcript, or meta artifact. This is not waivable by a suite.
- **Instrument liveness**: a run of a cell that produced zero trace records is reported as BROKEN, never as an abstention, a pass, or a vacuous result. A single-prompt cell with an empty trace is the canonical case. Liveness is also enforced **at spawn, fail-fast** (ruling S8): if the server under test exits, or fails to advertise its tools, before the consumer turn begins, the cell is BROKEN at that moment and the model turn is not spent — and the breach is surfaced to the operator as it happens, because an operator watching a run must be able to distinguish in-flight from broken. Grounded in the first real suite's first run (2026-08-31): a cwd-dependent launch command died at spawn with `server_exit` faithfully recorded in the proxy meta, yet three cells of model turns were spent against a dead server while the consumer answered from priors and the operator read the run as hung.

## Layer 2 — consumer-behavior findings (human/spec-scored)

What the pinned `pass`/`fail` criteria govern: did the consumer, given honest tool responses, produce an honest answer — completeness caveats propagated, absence reported as absence, no fabricated citations, provenance carried through. A failure is classified before it is filed:

- **Consumer-behavior finding** — the tool told the truth and the model dropped it; a response-shape or prominence question for the server's spec.
- **Tool defect** — the trace shows the server violating its own published contract.
- **Instrument defect** — the harness, driver, or cell configuration could not have captured the signal. Fix the instrument before any disposition; no finding of any other class is recorded from a defective instrument.

**Answerless turns are classified by cause, never lumped into harness failure (ruling S13, 2026-09-18).** A turn can end without an answer because the instrument broke (a harness failure: the cell is BROKEN) or because the consumer ran itself into a limit — an endpoint refused a request that the consumer's own tool calls had grown past the endpoint's context length, or the scaffold's step cap ended the loop. The second kind is a **consumer outcome**: the instrument captured everything, the trace is complete, and the suite's criteria score the row as a consumer that failed to answer. Artifacts carry a distinct outcome for it (name is the implementation's; `consumer_limit` with a cause of `context_length` or `step_cap` is the suggested shape) with `harness_failure` null, and the run report counts it beside pass and fail, never under broken. Grounded in `runs/2026-09-18-q8-data-policy/deny-r05`: the consumer paged three ~413KB windows into context, the endpoint refused the fourth request at 160,645 tokens against a 131,072 limit, and the row read as a harness failure although it is exactly the paging behavior the prompt's own fail clause names. The distinguishing rule is mechanical: a 4xx on a request whose recorded size exceeds the served endpoint's listed context length, after at least one tool call, is a consumer limit; any other upstream error stays an instrument outcome.

**A final message with no content is its own recorded outcome, never an answer (ruling S16, maintainer, 2026-09-21).** S13's family gains a member that is not a limit. Observed by the uscode-mcp spec session and confirmed here from the artifacts of `uscode-mcp/runs/2026-09-21T01:13:27-04:00-loop-complete` (harness 0.1.0, `openai/gpt-oss-120b` @ `deepinfra/bf16`, reasoning low, temperature 1.0): **7 of 26 rows** carry an `answer.txt` whose whole content is the four characters `null`, with `answer_chars: 4`, `harness_failure: null`, `consumer_limit: null`, and the one digest `74234e98afe7498f` — which is SHA-256 of the string `null`, so the harness serialized a JSON null and then hashed and counted it as an answer. In all four such rows that have a session file (`loop-floor` C3, C4, D1, D3) the final assistant message has `content: null`, no `tool_calls`, and a `reasoning_details` text that ends in a JSON object shaped like arguments to an offered tool (`{"query":"AUKUS","page_size":5}`), and the final wire line reads `finish_reason: stop`: the model wrote its next tool call into the reasoning channel, and the turn ended call-free. The three fresh-cell rows (`loop-isolation` A5, C4, D3) show the `null` answer and the `stop` and have no session file, so the reasoning-tail half of the signature is **unobservable** there — the reason the harness must record the classification itself. The contract: (i) the row's answer is the final message's content when that is a non-empty string, and nothing else is ever an answer — null or empty content yields an empty `answer.txt`, `answer_chars: 0`, no digest, and the row is not counted in `answered`; the text `null` is never written. (ii) The row records a distinct consumer outcome with `harness_failure` null — suggested shape: S13's block with cause `null_final_content` — counted beside the limits in the run manifest, never under broken and never as an answer. (iii) The loop consumer, which sees the whole response, records two derived marks with it: whether the final message's reasoning text ends in a parseable JSON object, and which offered tools' parameter names cover that object's keys; and the final `finish_reason` as already recorded. Marks are booleans and tool names and carry no text; the text itself belongs in the row's consumer transcript, which "Recorded per cell, per run" below already requires and which fresh loop rows in that run do not have (crowded rows have it as the `loop-session-*.json` file; the fresh rows' directories hold no message list at all) — a conformance gap, ordered closed in WO-7, and the reason three of the seven rows could not be fully read. (iv) Whether the fault is the model's or the serving stack's tool-call parser is not separable from here and is not claimed: it is a property of server × model at that endpoint, which is what a loop cell measures, and the suite scores the row as a consumer that failed to answer. (v) This is recording, not loop policy: `loop-scaffold@1` and its hash are untouched, and rows on either side of the fix are the same instrument. Rows recorded before the fix are identifiable after the fact by `answer_chars: 4` with digest `74234e98afe7498f`. Dead-defensive check on the harness's own record: zero of the 86 `answer.txt` files under `runs/` are a literal null, so no acceptance record here counted one. Ordered in WO-7.

## Run mechanics

Live consumer per run; no replay tier. Runs are minimal and manual: high-risk changes and pre-release, at the suite owner's discretion.

**Repeats are a run parameter (ruling S15, maintainer, 2026-09-21).** `mcp-e2e run --repeats N` invokes every selected (cell, prompt) pair N times in one run. N belongs to the run and never to the manifest: the manifest hash is untouched, so rows from a repeated run, from N separate runs, and from different arms stay comparable on the usual rule. Binding details, the spec session's: (i) **every repetition is a whole invocation** — fresh neutral working directory, fresh server process, `setup` re-run, crowding pre-turn re-run (S5 admits no warm-by-accident, and a repetition that inherited the last one's server would be exactly that); the loop calibration probe stays once per cell per run, as now. (ii) **Repetition is the outer loop:** the runner makes pass 1 over the whole selected grid, then pass 2, and so on, so that arms compared within one run are interleaved in time — a provider's bad quarter-hour lands on every arm and not on one — and a budget stop leaves the arms with counts that differ by at most one. (iii) **Layout:** when the flag is given, including `--repeats 1`, a row lives at `<cell>/<group>/<prompt id>/rNN/` (two digits, 1-based, wider only if N needs it); when it is absent the layout is what it always was, so no existing reader or cited path breaks. Readers key off the artifacts and not the path: every row's `meta.json` carries `repetition` (1-based; null without the flag) and the run manifest's `selection` carries `repeats` (null without the flag). (iv) **Budget and estimate:** the pre-run estimate and stated invocation count multiply by N; cap semantics are unchanged, and a cell-cap stop skips that cell's remaining prompts and repetitions. (v) **The answers count becomes real:** per prompt within a cell, `answers` records `invocations` (rows attempted), `answered` (rows with a non-empty answer), and `distinct` with `digests` over the answered rows only — an answerless row (a consumer limit, a harness failure) has an empty answer, and N empty answers hashing alike would read as N replays of one draw; that case is reachable (`runs/2026-09-18-q8-data-policy/deny-r05`). (vi) Layer-1 checks evaluate over all repetitions' records, and a failure reference gains the repetition (`30-checks.md`). Nothing here makes a repeat a sample — `50-drivers.md` → loop, requirement 11 stands, and the flag is what finally lets one run manifest show the distinct-answer count that requirement asks for. Preregistered with the order (WO-6, part B): expected — under the fake upstream, three repetitions of one pair where the fake returns two different answers record `invocations: 3, answered: 3, distinct: 2`, three server spawns, and `setup` recorded in each repetition's meta; falsifier — any repetition whose artifacts show a reused server process or a missing setup record, or a count that disagrees with the three `answer_sha256_16` values.

**WO-6 part B accepted (2026-09-21, spec session, from `runs/2026-09-21-wo6/`, report read second; commit 5d0364a).** Preregistered outcome met, no falsifier observed. Read from the artifacts of the `--repeats 3` run: six rows at `<cell>/A/A1/r01..r03`, each `meta.json` with its `repetition`; six distinct server spawn pids in `proxy-meta.json` → `server_spawn` and six distinct working directories; a `setup` record with its response in every repetition; `started_utc` ordering control r01, treatment r01, control r02, treatment r02, and so on — the outer loop as ruled; `answers.A1` reading `invocations: 3, answered: 3, distinct: 2` for each cell, agreeing with the three `answer_sha256_16` values, each of which the spec session recomputed from `answer.txt`; `selection.repeats: 3`; the pre-run output stating 6 invocations and a per-cell estimate for 3. The answerless run reads `invocations: 3, answered: 2, distinct: 1` for the affected cell, the row a `consumer_limit` with `harness_failure` null. `--repeats 0` is refused as a usage error. **The flagless comparison, and a defect in the work order that the implementation reported and did not paper over:** paths identical (33 files before and after), no key removed; keys added are `repetition` and `selection.repeats` (null), and also `env` in row meta, `answered` in every `answers` block, and the per-cell and row-naming fields of the checks report. WO-6's text said a flagless run would differ by the two null fields only, which contradicted its own part A and its own item 12 — the spec session's drafting error. Ruling: the contract for a flagless run is **identical paths, no key removed or changed in meaning, additions only as ordered**; the work order is corrected to say so. One observation outside WO-6's scope, recorded here so it is not lost: the answerless replay was classified a consumer limit from the endpoint's own stated numbers although the request (~379 tokens) was far under the listed context length (131,072); S13's operational form in `50-drivers.md` gives the listing precedence, so which source wins when both exist and disagree is worth a look the first time a live row raises it — the fake was built to produce the shape, and no live row has.

**Attribution — the two-source rule.** The cell's environment must make answers attributable to exactly two sources: the model's priors and the server under test. Binding consequences:

- Web/network and other non-server tools disabled, and their absence **verified by observation, not asserted from configuration** (ruling S7). A driver flag that requests disablement is a claim; it was measured insufficient on 2026-08-31, when a driver's deny-flag blocked invocation but left every builtin on the consumer's surface. The verification tiers: where the driver's model-API traffic can be transparently interposed, the harness records the actual tool surface sent to the model on **every scored invocation** — wire-level ground truth, invisible to the consumer; where it cannot, a discarded same-configuration calibration probe gates merge-gating cells, valid only per recorded driver version. A disallowed tool observed on the wire, or a capture that saw zero model requests, is an instrument breach — never a clean row.
- No persistent memory, and a neutral working directory outside both the harness repo and the suite repo, so no CLAUDE.md, spec file, or repo context leaks into the consumer. A consumer that learns it is being tested, or what the internals look like, is a different consumer (the no-disclosure principle).
- A driver that cannot verifiably satisfy this (e.g. cannot disable its own web fetching) is refused for attribution-dependent cells; the harness fails the cell as instrument-broken rather than running it unattributable.

**The wire recorder's recording contract.** The recorder that provides S7's API-boundary capture is strictly transparent — it never originates, modifies, or reorders traffic; it only observes. What it records per request: path, model, tool names with their `tool_source`, body keys, and (added 2026-09-02, for context-accounting measurements such as uscde-mcp's E15) the serialized body size in bytes (decompressed where parseable; wire bytes with the encoding named otherwise). It records **no** headers, no message content, no tool schemas. Response bodies are recorded only via an explicit allowlist of named scalar extractions, which currently has exactly one entry: the numeric token count returned by a count-tokens endpoint (the endpoint of whichever API shape the driver speaks; one entry, because it is one scalar for one purpose), when the driver itself made that call — recorded on that request's own line. Extraction decodes whatever response encoding the driver negotiated (the recorder cannot narrow the negotiation without modifying traffic); an encoding it cannot decode is recorded as a null scalar with the encoding named, and counted in the per-cell digest as a call whose scalar went unread — a failed read is never recorded as an absent call (DR-3). **Entries added 2026-09-18 for the loop driver** (`50-drivers.md` → loop, requirements 4 and 6; measurement that needed them: `openrouter-probe-2026-09-18.md`, served-provider variation and per-request cost), all from the OpenAI-compatible chat-completions response: `provider` (the served-provider string), `usage.prompt_tokens`, `usage.completion_tokens`, `usage.completion_tokens_details.reasoning_tokens`, and `usage.cost` — five scalars, recorded on the request's own line, null with a note when absent or unreadable. **Sixth entry, added 2026-09-18:** `choices[0].finish_reason` (measurement that needed it: three pinned loop C1 completions sat at the 4,096-token `max_tokens` cap with ~20k-character answers cut mid-paste, and no artifact could tell a cap-truncated answer from one the model ended itself; a scorer reading claimed-versus-delivered must be able to). The loop consumer itself reads the full response, as any consumer does; the allowlist governs what the recorder writes into artifacts, never what the consumer sees. **Timing (added 2026-09-18, WO-1 finding 5):** each line records `at` as request arrival and `duration_ms` from arrival to the end of the response; a reader timing a slow backend from `at` alone was misled by a 356-second completion whose two lines sat 4 seconds apart. Because a line is complete only when its response is, lines land on disk in completion order; `seq` is assigned at arrival and is the order to read by. Growing the allowlist is a spec commit here, never an implementation convenience — each entry names the endpoint, the scalar, and the measurement that needed it. Per S10, this recorder is the only admissible source for claims about what reached the model; sizes and counts are scalars, so nothing new becomes publishable from artifacts.

**Knobs are recorded in the driver's native vocabulary, verbatim, never translated across vendors.** A Claude cell carries `thinking`; another vendor's cell carries that vendor's terms; no mapping between vendors' scales is recorded or implied, because none is defensible.

**Crowding is part of the instrument** (ruling S6). The `crowded` context condition is produced by a harness-owned, versioned crowding procedure: a coherent, mundane, domain-neutral task the consumer is genuinely mid-way through when the prompt lands, with other tools registered. Suites select a procedure by name; they never author crowding content, because the crowding sits in the consumer's context during the scored turn and a suite's spec session — which knows the internals — would be writing part of the instrument it is scored against (the same disqualification-by-construction that bars it from authoring real-user prompts). Trivia padding is rejected as the default on the design assumption that padding yields tokens without a competing goal and therefore under-crowds; that assumption is empirical and its settling measurement is recorded in `90-open-questions.md` Q5, not asserted here. No fixed corpus is inert for every server, so suite authorship includes a **domain-collision attestation** for the selected procedure; on collision the suite selects a different harness procedure.

**Setup actions, never model turns.** A cell may declare setup actions (see `20-manifest.md`): direct calls the harness makes against the server before the prompt — pre-warming a cache, seeding state. These are performed server-side by the harness, never by a model turn, and exactly what was done is recorded in the cell's meta artifact.

**Recorded per cell, per run:** manifest content hash; cell id and the full knob set; the complete tool-call trace; the consumer transcript; the recorded available-tool surface; setup actions performed; for crowded cells, the crowding procedure's name, version, and content hash; and a meta record (wall clock, tool-call count, and the upstream identifiers actually hit, so staleness of groundings is detectable after the fact rather than assumed away); and, when the suite declares them, row measurements (`30-checks.md` → "Row measurements"), recorded beside the row with their method name and hash, never as outcomes. The minimum trace-record fields are pinned in `30-checks.md`, since checks evaluate against them.

**Operator legibility** (ruling S9). The runner is never silent: it reports progress to its controlling terminal as it works — which cell and prompt it is on, turn transitions within a cell (setup, pre-turn, scored turn), and per-cell completion with at least wall clock and trace-record count — and it names the run directory up front, so an operator who suspects trouble knows where the artifacts are before anything has gone wrong. Format is the implementation's; the requirement is that the three states an operator must distinguish — in-flight, hung, broken — are distinguishable from the terminal without digging. Grounded in the DR-1 incident: the runner emitted nothing, so a progressing run was read as hung, and a run that was in fact broken (dead SUT, priors-only answers) was diagnosed only when the operator escalated — the artifacts held everything needed, but nothing pointed at them.

Run bytes land in a gitignored `runs/` directory — bytes are disposable; the scored findings are what gets committed, in the suite repo.

## Cells

A cell is identified by (driver, model, knobs, tool surface, context condition, setup, env, prompt selection), plus any identity components the driver's contract in `50-drivers.md` adds (the loop driver adds scaffold version and provider pin — S11). **`env` joined the tuple on 2026-09-21** (spec session; prompted by the uscode-mcp spec session's A/B arms, which are cells identical except for one server environment variable): S5 names `setup` and `env` as the two channels by which state reaches the server, `setup` was already in the tuple, and leaving `env` out was an omission, never a position — two cells whose servers run under different environments are measuring different servers. Secret-valued entries join identity by key name only, since the value may appear in no artifact. Observed the same day, from `runs/2026-09-18-wo3-examples/length/loop-cell/A/A1/meta.json`: the recorded `cell_id` string (`loop/fake/model-1/fresh/full/scaffold:loop-scaffold@1/pin:fakeprov/bf16`) carries neither knobs, setup, nor env, so it under-identifies cells today and rows are told apart by the manifest cell name plus the manifest hash; conformance is ordered in WO-6. The grid grows only when a question needs a new cell. Four roles recur and are recommended as the starting grid, but the roster is the suite's choice:

| role | what it isolates | typical shape |
|---|---|---|
| floor | the merge-relevant result: what a distracted mid-task consumer does | mid-tier model, no extended thinking, crowded context, full tool surface |
| ceiling | whether the data supports a correct answer at all | top model, high thinking, fresh context, question first |
| capability-floor | weakest-consumer behavior without conflating chaining limits with tool defects | small model, single-step prompt variants only |
| isolation | tool-selection noise vs tool-design defects | surface restricted to exactly the tools under test |

Attribution-dependent conclusions (e.g. "citation absent from the trace") hold **only** in cells where the trace scope equals the tool surface — the isolation role exists for that.

Cross-vendor cells never silently substitute for a gating cell of the primary vendor: a cross-vendor cell carries a distinct role and is non-gating unless the suite explicitly rules otherwise.

## Grounding rules for manifests

Adopted whole from the ancestor suite, where writing prompts from plausibility instead of the record invalidated three of them (A3, B3, E3 — see the example's annotations):

- Every prompt asserting a property of the server's data cites its grounding: a named, dated, reproducible measurement, or an observation recorded in the suite's spec.
- **Live-upstream staleness**: when the server fronts a live upstream, groundings are pinned against a stated snapshot (edition, date, content hash — whatever the domain offers). When the upstream moves, every grounding that depends on it is stale: re-measure before scoring any run against it. The per-cell meta's record of upstream identifiers actually hit is what makes staleness detectable.
- **Real-user prompts** (the ancestor's Group F): prompts meant to represent real use must be verbatim questions from real sessions, authored by no one who knows the server's internals — the suite's spec session is disqualified by construction. Every prompt carries a `sourcing` field; anything not `verbatim-original` is scored as indicative only, never as a measurement. A prompt with null `pass`/`fail` must name a pinned rubric instead (`20-manifest.md`).

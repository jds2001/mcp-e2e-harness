# WO-1 — Loop driver: OpenRouter deployment, real floor models

**Issued:** 2026-09-18, spec session. **For:** the implementation session. **Spec authority:** `50-drivers.md` → loop (requirements 1–10), `20-manifest.md` → "Loop-driver cells", `10-harness.md` → recording contract (allowlist as of 2026-09-18), `00-INDEX.md` S11 and S12, `90-open-questions.md` Q8, `SUITE-AUTHORING.md` → "Real floor models". On any conflict between this document and those files, the files win; report the conflict rather than resolving it locally.

## Goal

Make `"driver": "loop"` runnable against OpenRouter so a suite can put a real, cheap floor model (first target: `openai/gpt-oss-120b` pinned to a bf16 endpoint) into a crowded floor cell and a fresh isolation cell, with every attribution and legibility obligation the spec already places on the other two drivers, and then produce the Q8 settling runs under the harness's own recorder. The measurements in `openrouter-probe-2026-09-18.md` were made with an ad-hoc script; they tell you what to expect, and nothing there counts as verification of your driver.

## Deliverables

1. **The loop consumer.** A minimal MCP client plus tool loop over the OpenAI-compatible chat-completions API. It connects to the suite's server through the existing trace proxy (so `trace.jsonl`, `available-tools.json`, `proxy-meta.json` are produced exactly as for the product drivers), offers the server's advertised tools as the request `tools` array (filtered to the cell's `tool_surface`), executes tool calls against the server, and loops until the model stops calling tools or the scaffold's step cap is hit. The final assistant text is `answer.txt`. Crowded context must work: the crowding pre-turn (procedure from `40-instruments.md`, distractor server registered) runs in the same conversation before the scored prompt, exactly as the claude-code driver does it, because the floor role is crowded by definition.
2. **The scaffold as instrument content (requirement 1).** System prompt, tool-loop policy, step cap, and the calibration-probe tool definition live in one harness-owned, versioned unit with a `content_hash()` like the crowding procedure. Name it `loop-scaffold@1`. Keep the system prompt short, generic, and domain-neutral; it must not mention testing, harnesses, or evaluation (no-disclosure, `10-harness.md`). Put the scaffold's full text in your report so the spec session can review and pin it in `40-instruments.md`; the pin is the spec session's commit, the hash and the content are yours to report.
3. **Named deployment `openrouter`.** Base URL and credential (`OPENROUTER_API_KEY` from the harness's environment) are harness configuration. A manifest carries neither. Missing key at run time is a load-time refusal with a clear message, not a mid-run failure.
4. **Manifest schema and validation** for loop cells per `20-manifest.md`: `endpoint`, `model`, optional `provider`, required `scaffold`, `knobs` verbatim, optional `data_policy`, optional `budget_usd`. Explicit `null` ≡ absent (DR-2). Reject `model` ids carrying a routing suffix such as `:free`.
5. **Provider pinning and strict routing (requirements 4, 9; S12).** Every loop request sets `provider.require_parameters: true` and `provider.data_collection: "deny"` unless `data_policy: allow`. A pinned cell additionally sets `provider.order: [<slug>]`, `allow_fallbacks: false`, and `quantizations: [<q>]` when the pin tag names one (`deepinfra/bf16` → slug `deepinfra`, quant `bf16`). The served provider is read from each response's `provider` field and recorded per request; on a pinned cell a mismatch BREAKS the cell (`harness_failure` set, surfaced live). An unpinned cell records the served-provider set and stamps `reproducibility: unpinned` on every row it emits, in `meta.json` and in the checks report.
6. **Calibration probe (requirement 9).** Before the first scored turn of any (model, provider, scaffold, driver-version) tuple: one discarded invocation under the cell's exact knobs and pin, offering only the scaffold's probe tool, asking for a lookup by key. Pass = exactly one tool call, correct name, JSON arguments valid against the schema. Cache the verdict with the date under the run directory's parent or a harness cache dir, keyed by the full tuple; a miss or a fail refuses the cell as instrument-broken before any model turn is spent (S8 kin). The probe's request goes through the same recorder as scored requests and its line is marked as a probe, never counted among scored requests.
7. **Wire recording (requirement 2; `10-harness.md` allowlist).** The loop's own outbound traffic passes through the recording proxy — the recorder observes bytes, it does not receive a copy of what the loop intended to send. Per request line: everything the recorder already writes (path, model, tool names, body keys, `body_bytes` and basis, encoding) plus the five loop scalars added to the allowlist on 2026-09-18: `provider`, `usage.prompt_tokens`, `usage.completion_tokens`, `usage.completion_tokens_details.reasoning_tokens`, `usage.cost` — null with a note when absent. Nothing else from any response body. Message content, headers, and tool schemas stay out, as everywhere.
8. **S7 check per request (requirement 3).** The recorded `tools` array must equal the cell's surface exactly on every scored request; any extra name is a breach, cell BROKEN. This is the same check the claude-code driver runs; reuse it.
9. **Cost legibility (requirements 6, 10).** Before the first invocation the runner prints: invocation count; an estimated spend from the catalog's per-model list price and the byte-based token estimate in `50-drivers.md` (labeled estimate; reasoning tokens named as the unbounded term); and the applicable data policy per pinned provider. A run-level budget flag and per-cell `budget_usd` are honored: the run stops cleanly at the cap, completed cells stand, and the stop is a run-level outcome in `run-manifest.json` and on the terminal. Actual `usage.cost` is summed per cell and per run into meta.
10. **Family and identity marks (requirement 8; S11).** Every artifact that names a cell — `meta.json`, `run-manifest.json`, `checks-report.json` — carries `driver_family: loop`, `scaffold: loop-scaffold@1` with hash, the provider pin or `unpinned`, and the served-provider set. Product-driver cells are untouched.
11. **Tests for all of the above**, per the repo rule, including: the probe pass/fail/cached paths; strict-routing fields present on every request; mismatch → BROKEN; unpinned → mark present in every artifact; budget stop; allowlist confined to the five scalars plus the count-tokens entry; suffix rejection; crowded pre-turn ordering. Fake upstream, no network in tests. `ruff` clean.

## Q8 settling runs — do these after the driver passes its own tests

Use the uscde-mcp suite (its C1 prompt exercises a large tool result and a second call) unless the maintainer names another. Keep total spend under **$2**; the pre-run estimate will tell you before you commit. Record each run under `runs/2026-MM-DD-q8-<name>/`.

- **P-tool-probe:** the roster in `SUITE-AUTHORING.md` at the pins named there, via the calibration probe. Expected: all well-formed. Report the served providers.
- **P-provider-pin:** ≥10 invocations of one pinned cell (`openai/gpt-oss-120b` @ `deepinfra/bf16`, isolation, C1); expected served == pin on every request. Baseline: the same cell unpinned, ≥10 invocations; report the served-provider set. A response lacking `provider` is a mismatch, not a pass.
- **P-knob-drop:** reproduce the 2026-09-18 observation under the harness: `openai/gpt-5.4-nano` pinned to `openai` with `temperature` in knobs. Expected: refused at request time with the refusal surfaced as a cell breach naming the parameter, never a silent success. Then the same cell without `temperature`: runs normally.
- **P-data-policy-routing:** ≥10 invocations of an unpinned `openai/gpt-oss-120b` cell with the deny default; report the served-provider set and, for each provider in it, whether OpenRouter's endpoint listing marks it as logging. State plainly that this measures routing against published metadata, not backend behavior.

## Acceptance — what the spec session will read

Artifacts, not the summary. For each deliverable, name the run directory or test that shows it. Expected in the report:

- The scaffold's full text and `content_hash()`.
- The exact key names you chose for: served provider, the four usage scalars, the probe verdict, the reproducibility mark, the family and scaffold marks, and the budget stop outcome — with one example line from a real run for each.
- For each Q8 run: run directory, invocation count, per-request served providers (a set with counts is fine), total `usage.cost`, and any breach raised.
- Total spend actually incurred, from summed `usage.cost`.
- Anything in the spec you found unimplementable, contradictory, or dead-defensive, stated as such — that is a finding, not a failure.

# WO-13 — interview mode: resume a scored loop row and ask the model why

**Issued:** 2026-09-23, spec session, on a request from the uscode-mcp suite (its text dated 2026-09-24; maintainer-approved there the same day). **For:** the implementation session. **Spec authority:** `10-harness.md` → "Interview mode" (ruling S21); `50-drivers.md` → loop; `00-INDEX.md` S10. Files win on conflict. Medium.

## Background

The trace shows what a consumer did and never why. The requesting suite names three rows this week where one question no artifact can answer would have been worth more than another repetition: a C4 row that called a tool with `max_chars: 0`, was refused, and never retried ("why did you stop?"); an after-arm row where the caveat's effect on the model is the residual behind two of its open items ("what did the caveat tell you to do, and who is the person asking?"); A5 rows that read an `ambiguous` response listing two rules and presented one as unique ("why did you not mention the second?"). Two of its findings were this instrument run by hand on capable consumers, and both measured real afterwards. The loop driver has the session file and the scaffold, so it can run the same thing on the floor.

What the harness is asked for: `mcp-e2e interview --row <row dir> --ask <text>` (repeatable) or `--ask-file <path>`, resuming the row's recorded session with the same scaffold, pin, and knobs, the tool surface mounted, and recording the exchange beside the row where nothing aggregates it. The identifiers in the request (C4, E26, A5, Q22, R25, S11, S18, F10, WO-12) are the requesting suite's, not this spec's.

## Deliverables

1. **The command.** `mcp-e2e interview --row <row dir> (--ask <text>)... [--ask-file <path>] [--budget-usd N]`. `--ask` may repeat; `--ask-file` is a JSON array of strings. Questions are put in order, each as one loop turn in a session that continues from the previous answer, so the second question sees the first exchange. Nothing else is added: no harness-authored preamble, framing, or system text — the operator's question is the only new content, sent as a user message byte-for-byte as given. If a question is refused by the endpoint or ends in a consumer outcome (S13's family, S16 included), that is recorded for that question and the interview continues to the next.
2. **Same context, honestly.** The replayed prefix is the row's recorded session file — messages and offered tools verbatim, under the row's scaffold (same hash), pin, knobs, and `require_parameters`. The interview records what it replayed: a digest of the session file it read, whether recorded reasoning content was sent back to the endpoint (`reasoning_replayed: true | false | null` with a note, since "why did you stop?" on an S16 row depends on it), and the served provider per request as for any turn. The MCP server is spawned fresh (S5); a tool the model calls during the interview answers from that fresh process, and the interview's own trace records it. Wire capture interposes exactly as for a scored turn (loop requirement 2); the S7 surface comparison runs and its result is recorded in the interview's meta, never in the row's.
3. **Eligibility.** Runs only on a loop row whose scored turn ran to a recorded end: `meta.json` with `driver_family: "loop"` and `harness_failure: null`, whatever the consumer outcome (answered, `null_final_content`, `step_cap`, `context_length`), and a session file present. Refused, with the reason on the terminal and nothing written, for: a product-driver row; a row with `harness_failure` set; an attempt directory that ended precondition unmet (S17) or `upstream_unavailable` (S20); a directory with no session file. A `context_length` row is eligible and will likely be refused again by the endpoint; that refusal is recorded like any other.
4. **Where it lands, and what.** `interview/NN/` under the row directory (two digits, 1-based; a second interview on the same row is `02/`, and an existing directory is never overwritten). Inside: `questions.json` (the questions verbatim, in order, each with its index), `interview-session.json` (the full transcript: the replayed prefix and every new message, one shape with the row's session file), `api-surface.jsonl` (the interview's own wire lines, same contract as a scored turn's), `trace.jsonl` (tool calls made during the interview), and `meta.json` carrying at least: `interview: true`, `aggregate: false`, the row's relative path, the row's `answer_sha256_16` and repetition, the session-file digest, scaffold name and hash, model, pin, knobs verbatim, `reasoning_replayed`, per-question `{index, finish_reason, tool_calls, served_providers, spend_usd, consumer_limit}`, and the interview total `spend_usd`. Shape beyond that is yours; the content is not.
5. **Nothing aggregates it.** The run manifest, `checks-report.json`, row measurements, cell liveness, `answers` counts, `invocation_counts`, slot states, and `report --run-dir` are unchanged by the presence of any number of `interview/` directories, and the row's own files are untouched (every file under the row other than `interview/` has the same digest before and after). Walkers that enumerate row subdirectories skip `interview/` explicitly — DR-4 was a walker meeting `attempt-02/`.
6. **Cost and legibility.** S9 and loop requirement 6 apply: the command names the interview directory up front, prints each question and its answer as they complete, states an estimate before the first request (basis: every question re-sends the whole prefix, so the row's final `usage_prompt_tokens` plus the exchange so far is the input term per question), and honors `--budget-usd`; a budget stop ends the interview cleanly, is recorded in the interview's meta, and never touches the run manifest. Usage and cost per request from response metadata, as for any turn.
7. Unit tests for 1–6 via the fake upstream; `ruff` clean; nothing under `documentation/`.
